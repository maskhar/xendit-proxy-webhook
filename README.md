# Xendit multi-tenant gateway and webhook router

One Xendit business account, separate tenant credentials and downstream webhook destinations. Node.js/Fastify/TypeScript API, PostgreSQL durable routing/delivery, worker, and optional Caddy TLS front end. Project is **implementation for local/Test Mode validation, not a live-ready payment service**. No production keys or live cutover are included. Payments still run through Xendit; gateway cannot replace Xendit account configuration or tenant application code.

## Boundaries

- Tenant-facing API is an explicit allowlist, not arbitrary Xendit passthrough: Payment Requests v3 (`POST /v3/payment_requests`, `GET`, `cancel`; gateway `PAY`/`REUSABLE_PAYMENT_CODE` with explicitly allowlisted `channel_code` only), Payment Sessions (`POST /sessions`, `GET`; gateway `PAY`/`PAYMENT_LINK` with optional `customer_id` only), and protected Refunds (`POST /refunds`). No inline customer/card details, token charging, `PAY_AND_SAVE`, or arbitrary provider fields. Empty tenant channel allowlist blocks direct Payment Request creation. Gateway paths use `/v1/...`; check actual route implementation and tests before integration. Legacy Invoice v2 (`POST /v2/invoices`) is a **distinct product**, not an alias for v3 or Payment Sessions. Current tenant-facing server **does not register** `POST /v1/legacy-invoices`; client method alone is not gateway support. Existing Invoice callbacks need legacy mapping/import while any old invoice remains open.
- Each tenant has an independently issued, scoped gateway API key. Mutations require `Idempotency-Key`; an operation is reserved before its provider POST. Unknown provider outcome remains `UNKNOWN` and **must not be blindly retried with a new key**. Query `/v1/operations/:id`, investigate Xendit Dashboard/API and webhook history, and reconcile manually. No unverified promise about Xendit v3 upstream idempotency or finding pending requests by reference.
- Webhooks must carry Xendit's `x-callback-token`; gateway requires matching business ID for Payments/Sessions/Refunds and Invoice (`user_id`, fallback `business_id`), rejects mismatching IDs on legacy callbacks when present. Environment separation relies on distinct deployment credentials/database and dashboard Test/Live settings, not an environment signature inside all webhook bodies. Gateway stores original body bytes, then routes only when owner is known; unsupported event types are quarantined. A retry that changes only envelope delivery timestamp is acknowledged as duplicate; same stable event identity with other changed content is acknowledged to stop retry storms, preserved in `webhook_conflicts`, and surfaced for admin review without new delivery. Unknown/conflicting events are retained, not broadcast. Worker sends original body with a **tenant-specific proxy token**, not Xendit's token. Downstream systems must deduplicate by event/payment/capture/refund identity: a worker crash after downstream 2xx can deliver again.
- Refunds require separate `refund:create` scope and explicit owned `payment_request_id`, `payment_id`, `amount`, `currency`, `reason`; gateway checks captured mapping and cumulative amount, then omits local-only `payment_id` from Xendit request. Because provider request targets `payment_request_id`, only gateway-created one-off `PAY` requests with exactly one mapped payment are eligible. Reusable/imported requests are blocked; a response without expected `payment_id` and `payment_request_id` remains `UNKNOWN` for reconciliation and its refund resource ID is not trusted as a route. Refund webhooks must match stored payment/request identities; first terminal `SUCCEEDED` or `FAILED` state is retained against out-of-order callbacks. No amount-omission/full-refund shortcut is exposed. Xendit refund response may be pending; confirm final outcome through `refund.succeeded`/`refund.failed` and provider records. **Do not treat request acceptance, redirect or session completion alone as settled funds.** Payouts/disbursements and arbitrary Xendit APIs are outside scope.

## Deployment layout

`compose.yaml` builds one image for `api`, `worker`, and one-off `migrate`; PostgreSQL 16 is private; Caddy exposes only ports 80/443 and proxies public API/webhook paths, not `/healthz`, `/readyz` or admin. API and worker have outbound networks for Xendit and downstream calls. Admin binds `127.0.0.1` **inside API container**, never through Caddy. Caddy domain is placeholder until real DNS/TLS. `APP_ENV=test` and `APP_ENV=live` **must not share** database, secret files, Docker Compose project, domain or Xendit credentials. **Changing `COMPOSE_PROJECT_NAME` alone does not isolate `./secrets/`**: deploy stacks from separate directories with separate secret files and distinct DNS. Production keys belong in mounted files, not `.env`, Compose YAML, image, logs, or git.

1. Copy `.env.example` to `.env`. Choose a unique `COMPOSE_PROJECT_NAME`, real `GATEWAY_DOMAIN`, correct `XENDIT_BUSINESS_ID`, `APP_ENV=test`, and verify DNS points to VPS before starting Caddy. Example hostname is not a real configured endpoint. Do not start live mode for a smoke test.
2. Create `secrets/postgres_password`, `secrets/database_url`, `secrets/xendit_api_key`, `secrets/xendit_callback_token`, `secrets/encryption_key`, `secrets/admin_token` outside source control. `database_url` contains `postgres://xproxy:<URL-encoded value of postgres_password>@db:5432/xproxy`; encode reserved characters in password. `encryption_key` holds a base64 32-byte key (`openssl rand -base64 32`). Use strong independent keys, restrict host file permissions, back them up securely. See `.env.example` for exact file contract. `DATABASE_URL_FILE` is required when `NODE_ENV=production`. Provider origin is pinned to exact `https://api.xendit.co`; `ALLOW_INSECURE_XENDIT_BASE_URL=true` is accepted only with `NODE_ENV=test` for isolated local fake-provider tests and must never appear in a deployment.
3. Run `docker compose config` to validate interpolations, then `docker compose up --build -d db migrate api worker` for isolated Test Mode (without Caddy) or `docker compose up --build -d` **only after** DNS, TLS, ingress and Test Mode configuration are reviewed. Check `docker compose ps`, migration output, application readiness `/readyz` and redacted logs. `/readyz` requires DB connectivity, at least one migration and a delivery-worker heartbeat newer than two minutes; API remains unhealthy until worker starts. Docker Compose dependencies handle startup ordering, **not** a complete rollout: verify state after every start. Compose does not create or issue tenant API keys or activate destinations automatically.
4. Configure seeded tenants and their destination/token/policies using private admin API tooling **after reviewing current routes and authentication**; admin CLI is not currently present despite historical script references. Existing admin routes can list seeded tenants, manage keys/destinations/policies, import exact references/resources, inspect unrouted/dead/unknown records, reroute supported events and replay eligible dead deliveries. They do **not** create future tenants, manage/dry-run legacy rules, import captured payment amounts, or resolve `UNKNOWN` operations. Seeded destination URLs are examples and disabled. Test each application independently. Never use real customer transactions as smoke data. Set dashboard webhook URLs only after legacy mapping/import and Test Mode verification; never alter live dashboard settings as part of this setup.

If Docker unavailable, `npm ci`, `npm run build`, `npm run typecheck`, `npm test` work with a local Node.js 22 installation. `test/integration/gateway.test.ts` is **skipped unless `TEST_DATABASE_URL` points to a migrated, disposable PostgreSQL test database**; unit tests alone do not verify deployment. Database-backed integration tests were run in a temporary PostgreSQL instance during implementation, but provider Test Mode and real downstream endpoints still require independent verification. Do not point integration tests at live/shared data: they insert keys and modify tenants/destinations. For local running, supply same env and secret file paths, start a separate PostgreSQL instance, `npm run migrate`, `npm start`, `npm run start:worker`. No defaults supply live credentials. `npm run admin` currently points to a missing CLI entry; use only reviewed private admin routes from trusted container/network and never expose port 3001 publicly.

## API shape (verify per route before integration)

| Gateway method/path | Purpose | Required scope |
|---|---|---|
| `POST /v1/payment-requests` | Create allowlisted v3 payment request | `payment:create` |
| `GET /v1/payment-requests/:id` | Read owned request from Xendit | `payment:read` |
| `POST /v1/payment-requests/:id/cancel` | Cancel owned request; mutation with idempotency key | `payment:cancel` |
| `POST /v1/payment-sessions` | Create hosted `PAY`/`PAYMENT_LINK` session | `session:create` |
| `GET /v1/payment-sessions/:id` | Read owned session | `session:read` |
| `POST /v1/refunds` | Request protected refund | `refund:create` |
| `GET /v1/refunds/:id` | Read locally recorded owned refund | `refund:read` |
| `GET /v1/operations/:id` | Read owned operation, including `UNKNOWN` | Corresponding read scope |

For create requests, send `Authorization: Bearer <tenant-gateway-key>`, `Idempotency-Key: <stable unique key 8..255 chars>`, and `Content-Type: application/json`. Client `reference_id` is retained; gateway sends a unique tenant-marked provider reference and reserves route before contacting Xendit. **Do not expect client metadata to return in webhook body**; resolve ownership via stored ID/reference mappings. Response includes `operation_id` and status, with `provider_response` when recorded; do not assume raw Xendit response or guaranteed synchronous success. Example (illustrative, not production credentials):

```sh
curl -X POST 'https://xendit-test.example.com/v1/payment-sessions' \
  -H 'Authorization: Bearer <tenant-gateway-key>' \
  -H 'Idempotency-Key: order-123-checkout-1' \
  -H 'Content-Type: application/json' \
  --data '{"reference_id":"order-123","session_type":"PAY","mode":"PAYMENT_LINK","amount":10000,"currency":"IDR","country":"ID","success_return_url":"https://store.example.com/paid","cancel_return_url":"https://store.example.com/cancelled"}'
```

Return URL hosts and currencies/channels must be configured for tenant; above URL will be rejected otherwise. For direct Payment Request and Refund examples, see [integration guide](docs/integration.md). No session status or HTTP redirect by itself proves payment settlement; verify relevant payment webhook or Xendit status.

## Webhook ingress and migration

Plan one gateway URL per **Xendit event category**, not one URL for every kind of webhook: `https://<real-domain>/webhooks/payments`, `/webhooks/sessions`, `/webhooks/invoices`, `/webhooks/refunds`, and `/webhooks/legacy` where matching event extractor/fixtures are verified. Route existence alone does not prove semantic support: ingress allowlists event names and quarantines unsupported names, but operator still must prove exact payload/ID extraction from real Test Mode fixtures. Payment v3, Payment Session, Invoice v2 and legacy channel callbacks can have different payloads and event settings. Confirm supported route paths, exact events and test payloads **before** changing dashboard settings. Xendit usually offers one URL per event setting; changing a shared URL can interrupt all five current websites at once. Its automatic retry is limited (up to six attempts); DB outage/non-2xx response requires monitoring and possible dashboard resend. Gateway 2xx after durable persist does **not** mean downstream acknowledged.

See [integration guide](docs/integration.md), [cutover checklist](docs/cutover.md) and [operations runbook](docs/operations.md). These spell out legacy import, five existing destinations, adding two tenants, Supabase authorization and rollback. **No live cutover, DNS/VPS modification, or Xendit Dashboard change is performed by this repository.**

## Release gates and unresolved work

Before any live traffic: pin base/Caddy images to reviewed immutable digests; run build/typecheck/tests (including integration tests against PostgreSQL and fake Xendit/tenants); verify exact incoming payloads and event categories in Xendit Test Mode; verify five downstream handlers accept gateway-issued tokens; decide legacy Invoice/VA/e-wallet coverage; import all historical mappings; dry-run conflicts; review refund eligibility and unresolved-POST reconciliation; prove backup/restore of database **and** encryption key; monitor quarantine/dead-letter/`UNKNOWN`/worker health; validate TLS/DNS/network rules; and get separate approval for each dashboard URL change. Runtime tests and deployment configuration alone do not establish live readiness.

Official references: [Payments API v3 migration](https://docs.xendit.co/docs/migrate-payment-api-v2-to-v3), [Payment Session migration from Invoice](https://docs.xendit.co/docs/migrate-to-payment-session), [refund](https://docs.xendit.co/docs/refund-payment-request), [webhook handling/retries](https://docs.xendit.co/docs/handling-webhooks). Confirm current product/account-specific contracts with Xendit before enabling live.
