# Operations runbook

Use with Test Mode first. Examples assume Compose stack from root directory; replace project/domain only after local verification. Commands that alter live data need explicit owner approval. Current admin surface is private HTTP `/admin/*` on API-container loopback port 3001 with bearer token; `npm run admin` points to a missing CLI entry and must not be treated as an available operator tool. Admin listener is not public through Caddy. Execute privileged actions through reviewed trusted container/network mechanism; never publish port 3001. Available routes include tenant listing, key/destination/policy management, exact mapping import, unknown/unrouted/dead inspection, event reroute, dead-delivery replay, and audit. No tenant creation, legacy-rule management/dry-run, captured-amount import or `UNKNOWN` resolution route exists yet.

## Health and diagnostics

- `docker compose ps` checks DB/migration/API/worker/Caddy service state. Internal API `GET /healthz` is process liveness; internal `GET /readyz` requires PostgreSQL connectivity, at least one applied migration, and any same-`APP_ENV` worker heartbeat newer than two minutes. Caddy does not expose either endpoint publicly; Compose probes the API container directly. Readiness proves recent worker loop activity, **not downstream reachability or successful delivery**. A successful public Caddy response alone does not prove worker delivery.
- Inspect redacted service logs: `docker compose logs --since=1h api worker db caddy`. Do not paste secret values, URLs containing credentials, webhook bodies, Authorization headers or full payment metadata into support tickets.
- Monitor counts and age of `UNROUTED`, `QUARANTINED`, webhook dedup conflicts (`/admin/events/conflicts`), pending/retry/dead deliveries, `UNKNOWN` operations, stale `RESERVED`/`IN_FLIGHT` operations, worker heartbeat, database space, TLS certificate expiry, HTTP 5xx and Xendit Dashboard delivery failures. No bundled dashboard/alerts: configure independent metrics, on-call alerting and capacity plan before Live.
- Xendit retries failed webhook responses (typically up to six, exponential over about 24 hours). If gateway cannot durably store a webhook, non-2xx should trigger provider retry. If it already stored event and returned 2xx, provider considers delivery complete even when downstream later fails. Inspect gateway queue and manually replay only after receiver repair. Downstream is at-least-once, not exactly-once.

## Unknown provider mutation

1. Freeze automatic repeats and duplicate business actions. Do not send another POST with a new idempotency key. Keep original request/operation ID, tenant, timestamps, amount, currency and gateway-generated provider reference.
2. Query tenant `GET /v1/operations/:id`, inspect Xendit Dashboard and authorized API records, webhook event history and operation audit. `UNKNOWN` means gateway cannot prove whether Xendit accepted call, not proof of failure. Stale `IN_FLIGHT` is equally ambiguous because process may have stopped immediately before or after network send; stale `RESERVED` means provider call was not durably started but still needs operator review. Admin unknown listing includes stale states after five minutes. An interrupted create may later produce webhook even if API response never arrived.
3. Correlate exact business ID, reference, resource IDs, amount/currency and timestamp with originating tenant. Import only verified resource/reference mapping through reviewed admin procedure. Escalate unresolved or duplicated money movement to provider/support and tenant operator. Never mark paid or send refund solely from `UNKNOWN`.
4. Document manual disposition and alert owner. No documented provider guarantee currently permits safe automatic retry of v3 create or lookup of in-flight call by reference.

## Routing and dead-letter recovery

- Unknown ID/reference: retain as `UNROUTED`. Conflicting candidate owners: `QUARANTINED`. Do not broadcast or use generic default tenant. Compare payload with authoritative historical records; import exact ID/reference and reroute only after owner verified. Regex legacy rule must be collision-free; test dry-run and audit reason.
- Before replay: fix downstream cause, verify token/URL/cert, compare event against recipient's dedup store, inspect attempt history and intended tenant. Replay only chosen event/delivery using tested admin operation; verify no duplicate fulfillment. 3xx/most 4xx indicate configuration/content problem, not transient retry; 408/429/5xx/network may retry within bounded schedule. Exhausted events require manual review.
- Worker crash after downstream 2xx but before acknowledgement can resend same raw body; consumer must be idempotent. `x-callback-token` sent downstream is tenant gateway secret, never Xendit token.

## Secrets and rotation

- Each Compose stack mounts `database_url`, `postgres_password`, `xendit_api_key`, `xendit_callback_token`, `encryption_key`, `admin_token` as files. Keep files unreadable to unrelated host users; do not commit/copy into image or store in shell history/logs. Test and Live stacks need different values and separate directories/projects; file permissions/ownership must allow container user `node` (UID 1000) to read mounted application secrets. Docker Compose file secrets inherit host permissions on some engines; check before startup. PostgreSQL user reads its own password secret. DB URL password must match PostgreSQL secret and be URL-encoded.
- Xendit callback token rotation: configure temporary old token via `XENDIT_PREVIOUS_CALLBACK_TOKEN_FILE` and secret mount, roll API, rotate Xendit Dashboard token, validate callbacks, then remove old token and restart API. This option exists in application config but **is not pre-mounted** by default Compose; add secret mount explicitly before using it. Do not disable verification for rotation.
- Rotate tenant gateway API keys with overlapping, separately scoped keys; revoke old after observing traffic. Rotate downstream proxy token in coordination with each tenant. Never reuse Xendit callback token downstream.
- AES encryption key backs encrypted destination secrets; losing it makes stored tokens/headers unreadable. Keep offline encrypted backup and test restore. Rotation needs explicit re-encryption procedure; replacing file alone breaks old ciphertext. Admin token grants privileged routing/replay actions; limit execution to trusted host/container. Destination updates keep existing `enabled` and `max_attempts` if omitted; a newly created destination stays disabled with 12 attempts by default. Set `enabled: false` explicitly to disable delivery before changing receiver configuration.

## Backup and restore

1. Define RPO/RTO and encrypted off-host backup schedule. Back up PostgreSQL (`pg_dump -Fc` or equivalent consistent snapshot) together with **matching** encryption-key file, secret inventory/rotation metadata, and tested migration version. Include Xendit event raw bytes, operation/reservation state, mappings, delivery queue and audit; loss may cause duplicate actions or misrouted callbacks. Never check dumps or key into repository.
2. Restore into isolated Test-only network first. Keep `APP_ENV=test`, test keys/domain and no live downstream destinations. Restore database and matching key, run migration check, verify table counts/ownership mappings, decrypt sample destination secret, reroute/replay controlled samples, verify worker resumes safely.
3. For live disaster recovery, freeze inbound DNS/webhook changes and worker until reconciled with Xendit event history and downstream dedup state. Imported historical mappings and provider outcomes must be rebuilt for all affected tenants before reopening gateway. A restored DB snapshot can be behind already accepted payments/refunds; never automatically replay unsent or `UNKNOWN` POSTs.

## Infrastructure limits

`compose.yaml` uses single PostgreSQL volume, one worker, one API and Caddy. No high availability, off-host backup, alerting, resource sizing, WAF or host firewall is supplied. Docker network separation is defense in depth: API has edge, private DB and outbound networks because tenant API calls require Xendit access; worker has private and outbound networks. Review container egress, private address/SSRF behavior, DNS rebinding, TLS policy, Caddy exposure and provider IP allowlisting with actual VPS operator. Health checks and successful local tests do not certify live payment safety.
